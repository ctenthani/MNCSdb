# V1.0 verification — 2 October 2026

66 tests passed; zero failures and zero skips. Integration checks ran with
PGlite 0.3.14 (actual PostgreSQL SQL execution) and JSDOM (DOM interaction).
No production Supabase connection, live accounts or email delivery was used.

## Database checks

- Complete V1.0 installer runs twice, and runs again after new judge/auditor roles,
  repeated requests and a certified result exist; these records are preserved.
- Own-association players, teams and results save directly; only competitions
  use council submission/approval. Other associations cannot read/write them.
- Association results publish with correct source labels and contribute to rankings.
- Three-team round robin produces exactly three distinct pairs; duplicate draws fail.
- Four-team knockout creates the full bracket, requires saved winning results and
  creates the final from advancing winners. Changing an advanced winner, entering
  two winning results or archiving generated dependent fixtures is rejected.
- Multiple independent funding requests are private to the association and MNCS.
- Rubrics/assignments lock when judging starts. Judges cannot read each other's
  ballots; submitted ballots cannot be replaced. Associations cannot submit ballots.
- Unverified email votes fail. Duplicate votes and direct voter-table reads fail.
- An assigned independent auditor certifies a confidential snapshot; MNCS cannot
  self-certify. Publication exposes scores/fingerprint without private ballots.
- A fan vote deliberately favors a different finalist from the judges' winner;
  the official result remains the judges' winner (83/100).
- The historical V0.9 SQL test intentionally runs the installer prefix before
  V1.0, to verify the migration baseline; the V1.0 SQL test verifies current behavior.

## Interface and account checks

- DOM interaction exercises athlete/team/result direct saves, competition council
  approval, fixture publication, ranking export and linked nomination drafts.
- Clicking the junior-female card selects that form and requires birth date.
- Persistent signed-in account display is present; funding forms omit unrelated
  leadership fields and save the request's correct payload.
- Awards DOM tests exercise rubric setup, judge assignment, sealed-ballot arguments,
  dossier access, auditor score display/certification and separate fan-vote submission.
- Tournament DOM tests filter eligible teams and submit seed order and correct
  conversion of Malawi local time to UTC.
- Netlify account tests provision both judge and auditor roles, and retain existing
  authorization, origin validation, private-key handling and password-reset checks.
- Existing registry, reporting, account, eligibility and legacy workflow tests pass.
